\section{Performance and Resource Analysis}\label{sec:performance-resource}

This section presents an empirical evaluation of the performance and resource consumption of the implemented authentication methods. We've seen that FIDO2 is the our most secure technology, but does it mean it will lack the performance of legacy systems?  Now we will delve into the end-to-end latency, server-side CPU overhead, and database load, comparing how the three implemented methods fared.

\subsection{Latency Analysis}

We analyze the latency of registration and login operations, excluding the time spent on the client device, research indicates this introduces a delay of 50--200 ms depending on the device \cite{wuersching2023platformvsroaming}. We think this is a more accurate representation of the server-side performance. The tests are conducted in an isolated environment to minimize external factor and lessen the scope of testing.

\subsubsection{Registration Performance}
Figure~\ref{fig:registration-comparison} shows the registration latencies for each method.

\textbf{Password Registration ($\approx$216 ms):} As we have mentioned in \ref{sec:implementation}, for the bcrypt hashing to be secure we have to use at least 10 salt rounds, for our implementation we use 12 salt round, which means that the algorithm runs 12 times and takes about 216 ms to hash a password.

\textbf{2FA Setup ($\approx$228 ms):} This method inherits the latency of password registration, and also adds a negligibly small overhead for secret generation, thus bcrypt step remains the bottleneck.

\textbf{FIDO2 Registration ($\approx$108 ms):} Since keygeneration happens on the client hardware, the server only has to verify the signature, not require to do any computationally expensive operations, like the aforementioned hashing \cite{lyastani2020kingslayer}.

\begin{figure}[h]
\centering
\includegraphics[width=0.45\textwidth]{figures/registration-latency-comparison.pdf}
\caption{Registration latency comparison. FIDO2 outperforms legacy methods by offloading cryptography to the client.}
\label{fig:registration-comparison}
\end{figure}

We can see that all the latencies are still within the realm of acceptability, but FIDO2 might be a better alternative at high loads, like at opening days of ticket sales for large scale events.

Login latency results are shown in Figure~\ref{fig:login-comparison}.

\textbf{2FA Login ($\approx$216 ms):} 2FA login is statistically identical to password login, since the HMAC-SHA1 check for the TOTP code is extremely fast.\cite{Kasemodel2025BlueTOTP}.

\subsection{Resource Usage}

\subsubsection{Computational Overhead}
Figure~\ref{fig:cpu-time-comparison} compares the server-side CPU time.

\textbf{Password/2FA:} These methods are CPU intensive. Every login burns server cycles on bcrypt. This limits scalability under high load.

\textbf{FIDO2:} This method is CPU efficient, since the heavy cryptography is offloaded to the user's device. The server only performs lightweight verification. \cite{lyastani2020kingslayer}.

\begin{figure}[h]
\centering
\includegraphics[width=0.45\textwidth]{figures/cpu-time-comparison.pdf}
\caption{Server-side CPU time comparison. FIDO2 significantly reduces server load by eliminating server-side hashing.}
\label{fig:cpu-time-comparison}
\end{figure}

\subsubsection{Database Load}
Database query analysis is shown in Figure~\ref{fig:db-queries-comparison}.

\textbf{Registration:} Password and 2FA flows often require multiple steps. This results in more database queries. FIDO2 registration is streamlined. It requires fewer round-trips to the database.

\textbf{Login:} All methods are highly optimized. They typically require only a single lookup. Database load is not a differentiating factor for login.
