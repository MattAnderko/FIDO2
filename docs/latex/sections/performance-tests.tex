\section{Performance Testing}\label{sec:performance}

This section presents empirical latency measurements comparing FIDO2, password-only, and TOTP authentication methods. The tests measure end-to-end authentication flows to provide a fair comparison of user-perceived performance.

\subsection{Test Methodology}

\subsubsection{Test Framework and Setup}
The latency measurements were conducted using a custom testing framework built on pytest with asynchronous HTTP client support. Tests run against an in-memory SQLite database and a fake Redis instance to ensure isolation and reproducibility. Each test executes multiple iterations (typically 10) to gather statistically significant data.

\subsubsection{Measurement Approach}
Latency is measured using high-precision timing utilities based on Python's \texttt{time.perf\_counter()}, which provides microsecond-level accuracy. Measurements are captured using context managers that wrap each operation, ensuring consistent timing boundaries. The framework measures:

\begin{itemize}
    \item \textbf{Endpoint latency}: Total time for HTTP request-response cycle
    \item \textbf{Operation breakdown}: Individual steps within complex flows
    \item \textbf{End-to-end latency}: Complete user authentication experience
\end{itemize}

\subsubsection{Test Scenarios}

\textbf{Password Authentication:}
\begin{itemize}
    \item Registration: Single API call to create user and hash password (bcrypt)
    \item Login: Single API call verifying password hash and issuing JWT token
\end{itemize}

\textbf{TOTP Authentication:}
\begin{itemize}
    \item Setup: Password verification + TOTP secret generation + QR code creation
    \item Login: Password verification + TOTP code validation (HMAC-SHA1) + token issuance
\end{itemize}

\textbf{FIDO2 Authentication:}
\begin{itemize}
    \item Registration: Three-step flow:
    \begin{enumerate}
        \item \texttt{/register/start}: Server generates challenge and credential options
        \item \texttt{WebAuthn create}: Authenticator creates key pair and attestation (simulated with 100ms delay)
        \item \texttt{/register/finish}: Server verifies attestation and stores credential
    \end{enumerate}
    \item Login: Two-step flow:
    \begin{enumerate}
        \item \texttt{/login/start}: Server generates authentication challenge
        \item \texttt{/login/finish}: Authenticator signs challenge, server verifies signature
    \end{enumerate}
\end{itemize}

\subsubsection{Fairness Considerations}
To ensure fair comparison despite different authentication complexities, measurements are taken at multiple levels:

\begin{enumerate}
    \item \textbf{Backend processing time}: Isolated server-side operations
    \item \textbf{Network round-trips}: Number of HTTP requests required
    \item \textbf{End-to-end flow time}: Total user experience (what matters most)
    \item \textbf{Cryptographic overhead}: Time spent on crypto operations (bcrypt, HMAC, ECDSA)
\end{enumerate}

The FIDO2 authenticator interaction is simulated with a 100ms delay, representing a typical hardware authenticator response time. This value is based on empirical observations of common authenticator devices (USB security keys, platform authenticators) which typically require 50-200ms for:
\begin{itemize}
    \item Key pair generation or signature computation
    \item User presence/verification (if required)
    \item Communication with the browser/platform
\end{itemize}
The 100ms value represents a mid-range estimate, allowing measurement of server-side processing while acknowledging that real-world FIDO2 performance varies significantly based on authenticator hardware (hardware security keys vs. platform authenticators vs. software authenticators).

\subsection{Analysis and Discussion}

\subsubsection{Key Findings}

\textbf{1. Registration/Setup Performance:}
FIDO2 registration (108ms) is faster than password registration (216ms) despite requiring two network requests. The difference stems from bcrypt hashing overhead in password registration. FIDO2 offloads cryptographic key generation to the authenticator, reducing server CPU load. TOTP setup (228ms) is the slowest, requiring password registration plus TOTP secret generation, backup code hashing, and QR code image generation. The QR code generation adds ~10-20ms overhead compared to password-only registration.

\textbf{2. Login Performance:}
FIDO2 login (~102ms) is faster than password/TOTP (~205ms), with the authenticator interaction (~100ms) being the dominant component. The server-side operations are minimal:
\begin{itemize}
    \item Challenge generation (~2ms)
    \item Authenticator signature generation (~100ms, includes user verification)
    \item ECDSA signature verification (~1ms)
    \item Database credential lookup
\end{itemize}
The authenticator delay represents hardware security key or platform authenticator response time, which varies by device but is typically 50-200ms.

Password and TOTP logins both require bcrypt verification, explaining their similar latencies (~216ms). TOTP adds minimal overhead: HMAC-SHA1 computation for code verification takes approximately 0.03ms, which is negligible compared to bcrypt password hashing (~200ms). The TOTP validation overhead is less than 0.02\% of the total login time, making it effectively invisible in end-to-end measurements.

\textbf{3. Network Round-Trips:}
FIDO2 requires two HTTP requests (start + finish) versus one for password/TOTP. However, this architectural difference does not significantly impact total latency in our measurements, as network latency is minimal in the test environment. In real-world scenarios with higher network latency, the two-request pattern may have more impact.

\textbf{4. Security-Performance Trade-off:}
FIDO2 provides superior security (phishing-resistant, origin-bound credentials) with acceptable performance overhead during registration. Once registered, FIDO2 offers both better security and better performance than password-based methods.

\subsubsection{Limitations}

The measurements have several limitations:
\begin{itemize}
    \item \textbf{Mocked authenticator}: FIDO2 tests use simulated authenticator responses. Real hardware authenticators may have different latencies (typically 50-200ms for user verification).
    \item \textbf{Local testing}: Network latency is minimal in test environment. Real-world deployments may see different relative performance.
    \item \textbf{Single server}: Tests run on a single machine. Distributed systems may show different characteristics.
    \item \textbf{bcrypt cost factor}: Password hashing time depends on bcrypt cost factor. Our implementation uses default settings; higher security requirements would increase password/TOTP latency.
\end{itemize}

\subsubsection{Implications}

For system designers choosing authentication methods:

\begin{enumerate}
    \item \textbf{FIDO2} offers the best combination of security and performance, especially for login operations. The registration overhead (~100ms authenticator interaction) is a one-time cost that pays dividends in faster, more secure logins.
    
    \item \textbf{Password-only} authentication has the highest latency due to bcrypt hashing, with no security benefits over FIDO2.
    
    \item \textbf{TOTP} provides two-factor security but offers no performance advantage over password-only, as both require bcrypt verification. The additional TOTP validation (HMAC-SHA1) adds negligible overhead (~0.03ms), which is less than 0.02\% of the total login time. The bcrypt password verification (~200ms) completely dominates the latency.
\end{enumerate}

These results support FIDO2 adoption for systems prioritizing both security and user experience, particularly for frequently-used authentication flows where login performance matters most.
